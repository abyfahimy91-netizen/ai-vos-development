# سند طراحی: کارنامه — از دیتابیس تا کسب‌وکار

**نسخه** ۱.۰ · **تاریخ** ۱۴۰۵/۰۷/۰۵ · **وضعیت** در حال اجرا

## ۱. تحقیق: چه کسانی این کار را کرده‌اند

### ۱-۱. الگوریتم استاندارد صنعت

منبع اصلی: *Understanding Diagnostics — The Diagnostic Plan* (صنعت خودرو). فرایند تشخیص، پنج گام ثابت دارد و هیچ سیستم خوبی این‌ها را دور نمی‌زند:

| گام | نام | معادل فارسی | خروجی |
|---|---|---|---|
| ۱ | Verify the Customer Complaint | **تأیید شکایت** | نشانه، بدون قضاوت |
| ۲ | Analyze the Problem | **تحلیل** | دامنهٔ مشکل، سیستم درگیر |
| ۳ | Isolate the Problem | **جداسازی** | آزمون‌ها تا رسیدن به علت |
| ۴ | Repair | **تعمیر** | قطعه + عملیات |
| ۵ | Verify the Repair | **تأیید تعمیر** | رفع نشانه |

**نتیجهٔ مهم:** جست‌وجوی ما نباید «حدس بزند»، باید **گام ۳ را اجرا کند** — یعنی سؤال بپرسد تا علت را ایزوله کند. این هستهٔ UX ماست.

### ۱-۲. بازیگران تجاری و مدل درآمدی

| بازیگر | چه می‌کند | درآمد از |
|---|---|---|
| **RepairPal** | بازارگاه دوطرفه؛ ۳٬۵۰۰ تعمیرگاه | معرفی سرنخ (lead) به تعمیرگاه |
| **CarMD** | دستگاه OBD + تشخیص + اتصال به تعمیرگاه | «CarMD Connect» — اتصال مستقیم فروش |
| **MECH AI** | تشخیص با AI + پیدا کردن تعمیرگاه | اشتراک + معرفی |
| **Autodata / Mitchell 1** | دیتابیس تعمیر برای تعمیرگاه‌ها | اشتراک B2B |

**نتیجهٔ کلیدی برای ما:** هیچ‌کدام از اینها با «فروش تشخیص» درآمد نمی‌کنند. مدل این است:

```
کاربر رایگان تشخیص می‌گیرد  →  قیمت و قطعه را می‌بیند
                            →  به تعمیرگاه‌های نزدیک وصل می‌شود  →  درآمد ما
```

یعنی **تشخیص، قیف (funnel) است نه محصول.**

### ۱-۳. وضعیت روز دانش فنی

- کاربردهای اخیر (۲۰۲۵-۲۰۲۶) روی **knowledge graph + LLM** برای تشخیص متمرکزند.
- اما برای ما این‌ها **الگوی داده** را یاد می‌دهند نه لزوماً راه‌حل را:
  `symptom → cause → test → part → cost` همان اسکلتی است که باید داشته باشیم.
- تصمیم ما: **موتور قاعده‌محور (rule-based) + گراف دانش**. LLM فقط لایهٔ اختیاری برای توضیح، نه برای تصمیم. چون تصمیم باید **قابل حسابرسی** باشد.

## ۲. الگوریتم: موتور تشخیص

### ۲-۱. اصل حاکم

> **موتور هرگز حدس نمی‌زند. یا دارد دلیل، یا نمی‌گوید.**

اگر برای یک مسیر داده نداریم، صریح می‌گوییم «نیاز به تکمیل» — و این خودش یک سیگنال برای تیم داده است.

### ۲-۲. جریان پنج‌مرحله‌ای

```
[۱] انتخاب خودرو ──────────────────────────┐
    (اجباری — بدون مدل، داده‌ها قابل استفاده نیستند)
                                              ▼
[۲] انتخاب سیستم/گروه ─────────────────────▶ مثلاً: موتور / برق / تعلیق
                                              │
                                              ▼
[۳] سلسله‌مراتب سؤال (Decision Tree)
    هر سؤال: چندگزینه‌ای، با «نمی‌دانم» و «هیچ‌کدام»
    هر پاسخ: مسیر بعدی را تعیین می‌کند
    پایان: رسیدن به علت‌های محتمل + آزمون بعدی
                                              │
                                              ▼
[۴] تبدیل علت → قطعه → هزینه
    علت ← sym_symptom_cause_test_statements (۹٬۷۴۷ رکورد موجود)
    قطعه ← parts + modiro_parts_prices_all (۴۶٬۹۸۰ قیمت)
    دستمزد ← modiro_labor_prices_all (۲۷٬۶۷۵ قیمت)
                                              │
                                              ▼
[۵] خروجی
    ✓ فهرست علت‌های محتمل با احتمال
    ✓ آزمون بعدی که کاربر خودش انجام دهد
    ✓ بازهٔ هزینه (کمینه / محتمل / بیشینه) به تومان
    ✓ قطعه‌های مرتبط
    ⚠ اگر داده کم بود: «برای این مدل اطلاعات کافی نداریم»
```

### ۲-۳. امتیازدهی علت (نه درخت صُلب)

برای هر علت محتمل، امتیاز از چهار جزء:

```
score = ( وزن نشانه        × تطبیق نشانه )
      + ( وزن سابقه خودرو  × تکرار در همین مدل )
      + ( وزن آزمون        × نتایج آزمون‌های انجام‌شده )
      + ( وزن فوریت       × urgency_code )

سپس نرمال‌سازی به احتمال ۰..۱
```

**چرا امتیاز به‌جای درخت صُلب؟** چون:
- دادهٔ ما ناقص است؛ درخت صُلب با یک شاخهٔ خالی کل مسیر را می‌شکند
- کاربر ممکن است نداند پاسخ را؛ گزینهٔ «نمی‌دانم» باید کار کند
- امتیاز اجازه می‌دهد «مطمئن نیستیم» را صادقانه بگوییم

### ۲-۴. ساختار دادهٔ لازم (۷ جدول جدید)

```
diagn_systems          سیستم‌ها (موتور، تعلیق، برق…)        ← codes.system_code دارد
diagn_questions       سؤال‌ها: متن، سیستم، والد، ترتیب
diagn_options         گزینه‌ها: متن، ارزش، «نمی‌دانم»
diagn_faults          علت‌ها: عنوان، سیستم، توضیح، فوریت
diagn_tests           آزمون‌ها: عنوان، روش، ابزار، زمان
diagn_rules           قاعده: نشانه → علت، با وزن
diagn_fault_parts     علت → قطعه، با احتمال و تعداد
```

## ۳. قیف کاربر (Funnel)

### ۳-۱. منابع ورودی

| منبع | حجم | نیت کاربر |
|---|---|---|
| جست‌وجوی «صدای تق پراید چیست» | ⭐⭐⭐ | **درد** — نزدیک‌ترین به خرید |
| جست‌وجوی «قیمت تعویض دیسک ۲۰۶» | ⭐⭐⭐ | **آمادهٔ خرید** |
| جست‌وجوی «ماشینم روشن نمی‌شه» | ⭐⭐ | اضطرار |
| «سرویس دوره‌ای پراید» | ⭐⭐ | نگهداری |
| «دفترچه ۲۰۶» | ⭐⭐ | مرجع |

### ۳-۲. نگاشت محتوا → قیف

هر نتیجهٔ جست‌وجو باید به **یک صفحهٔ تشخیصی** برسد، نه مقاله:

```
«صدای تق پراید»
        ↓
/diagnose/?car=SAIPA&pride&sym=knock   ← جادوگر شروع می‌شود
        ↓
۳-۴ سؤال → علت محتمل → هزینه → «تعمیرگاه نزدیک»
```

**این یعنی ۵۷۴۶ مقالهٔ موجود ما، ورودی قیف‌اند نه مقصد قیف.** هر مقاله باید یک CTA به جادوگر داشته باشد.

## ۴. خدمات چهارگانه

| # | خدمت | چه چیزی لازم دارد | وضعیت داده |
|---|---|---|---|
| ۱ | **جادوگر تشخیص** | سؤالات + قوانین | ⬜ صفر — باید ساخته شود |
| ۲ | **برآورد هزینه** | قیمت قطعه + دستمزد | ✅ **آماده** (۸۷ هزار قیمت) |
| ۳ | **مشخصات فنی** | car_specs | ✅ آماده (۵٬۰۴۱) |
| ۴ | **دفترچهٔ فنی** | متن + جدول | ⚠️ ۵۷ مگابایت متن، ۹۸ دفترچه قابل خواندن |

**خدمت ۴ جزئیات مهمی دارد:** دفترچهٔ فنی در ایران معمولاً **جدول سرویس دوره‌ای** است. UX باید تب‌بندی موضوعی باشد، نه یک متن طولانی.

## ۵. مدل درآمدی

```
مرحله ۱ (رایگان)     تشخیص + بازهٔ هزینه      ← جذب و اعتماد
مرحله ۲ (رایگان)     معرفی ۳ تعمیرگاه نزدیک    ← ارزش واقعی
مرحله ۳ (درآمد)      تعمیرگاه، هر ارجال = پول  ← مدل RepairPal
```

بازار ایران: تعمیرگاه‌ها شدیداً رقابتی‌اند و مشتری ندارند. **سرنخ آماده برایشان گران‌ترین کالای ممکن است.**
