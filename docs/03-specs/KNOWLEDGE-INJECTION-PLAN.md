## ۵) ⭐ قاعدهٔ طلاییِ برنامه: تزریق = «پیشنهاد»، نه «ورود»

> ⛔ **هیچ محتوایی مستقیم وارد جدولِ محصول نمی‌شود.** هیچ‌وقت.
> ⭐ چون: (۱) موتورِ ما «هرگز حدس نمی‌زند» — این قاعدهٔ خودِ پروژه است؛ (۲) سه نمونهٔ شکست داریم (نرمال‌سازی، OCR فیوز، رنگِ سیاه/سفید).

### ساکت‌ها (هر محتوا دقیقاً در یکی می‌ماند)
```
۱. خام (raw)      → فایل/متن + هش + منبع        ← هرگز پاک نمی‌شود
۲. استخراج        → رکوردهای ساختاریافته         ← «پیشنهادِ» ما
۳. بازبینی        → تأیید / اصلاح / رد           ← انسان یا قاعدهٔ سخت
۴. انتشار         → جدولِ محصول                  ← فقط گذرِ ۳
     └─ رد ⇒ rejected_rows با دلیل (نه حذف)
```

## ۸) ⭐ پیشنهاد به مینیس — بخش عملیاتی

### ۸-۱ یک «پیمانهٔ تزریق» به‌عنوان skill
یک اسکریپتِ واحد با **قراردادِ ثابت**، تا هر محتوایی که می‌دهید از یک مسیر رد شود:
```bash
./inject.sh --source <url|file|dir> --type <fault_profile|condition|price|safety|counterfeit|manual>
            --stage-only            # همیشه پیش‌فرض
```
⭐ گزینهٔ `--stage-only` **اجباری و پیش‌فرض** باشد. حذفش یعنی تزریق مستقیم — که ممنوع است.

### ۸-۲ ساختارِ پوشهٔ استاندارد
```
/opt/carnameh/ingest/
  raw/<yyyy-mm-dd>/<source_slug>/{meta.json, raw.txt, media/}
  staged/<yyyy-mm-dd>/<source_slug>/
      records.jsonl        ← پیشنهادها
      REPORT.md            ← چند رکورد، چند رد، چرا
      INGEST.log
  quarantine/<yyyy-mm-dd>/<source_slug>/     ← شکست‌ها با دلیل
  publish/                              ← فقط تأییدشده‌ها
```
⭐ `quarantine/` مهم است: ⭐ **شکست نباید پاک شود** — باید دیده شود، چون شکستِ سیستمیک را نشان می‌دهد (همان باگِ یوتیوب).

### ۸-۳ قراردادِ فایل (schema) — هر نوع محتوا یک شکلِ ثابت
هر رکوردِ `records.jsonl` **دقیقاً** این فیلدها را داشته باشد (و نه بیشتر):
```json
{"kind":"fault_profile","symptom":"…","cause":"…","test":"…","urgency":"high",
 "condition":{"when_cold":true},
 "negative_evidence":["اگر صدا فقط هنگام پیچیدن است، این خرابی نیست"],
 "differential":["دیسک","کالیپر"],
 "quote":"عینِ جملهٔ منبع","source_id":"SRC-…","locator":"صفحه ۱۲۳ یا ۰۳:۴۱",
 "confidence":0.7}
```
⭐ `negative_evidence` و `differential` **اجباری** باشند (می‌توانند خالی باشند، ولی **باید** کلید داشته باشند) — تا الگوی فکریِ «چه چیزی رد می‌کند» از روز اول در داده باشد.

### ۸-۴ قواعدِ سختی که مینیس باید رعایت کند
| # | قاعده |
|---|---|
| ۱ | ⛔ **هیچ `INSERT` مستقیمی در جدولِ محصول** — فقط `staged` |
| ۲ | ⭐ هر رکورد **بدون `quote` و `source_id` ⇒ رد خودکار** |
| ۳ | ⭐ هر اجرا **idempotent** باشد (اجرای دوباره = همان نتیجه، نه تکرار) |
| ۴ | ⭐ هر اجرا یک `REPORT.md` بسازد: چند رکورد · چند رد · **دلیلِ هر دسته رد** |
| ۵ | ⭐ اگر خروجی خالی بود ⇒ **هیچ فایل خروجی نوشته نشود** و اجرا «شکست» اعلام شود |
| ۶ | ⛔ تغییرِ اسکیما فقط با `CREATE TABLE ... IF NOT EXISTS` و ثبت در سند توسعه |
| ۷ | ⭐ بکاپ پیش از هر نوشتنِ گروهی |

### ۸-۵ نقشِ درستِ مینیس و AI
| نقش | ✅ درست | ⛔ غلط |

| استخراج | خواندن متن و تبدیل به رکورد ساختاریافته | ⭐ **«بروزرسانی» به‌معنای نوشتنِ مستقیم** |

| **پیش‌نمایشِ diff** | ببیند اگر تأیید کند چه چهیزی تغییر می‌کند | ⭐ بدون این، بازبینی خطرناک است |
| **کیفیتِ منابع** | `credibility_code` | ⭐ نمایشِ سهمِ «رسمی» در برابر «گفت‌وگو» (الان ۱٪ در برابر ۹۲٪) |
| ⭐ **شواهدِ منفی** | `G-30` — صفحهٔ اختصاصی برای ثبتِ «این علامت رد می‌کند» | ⭐ ورودیِ ارزان‌ترین قابلیتِ پرارزش |
| ⭐ **پوششِ دامنه** | برای هر سیستم: چند علامت · چند خرابی · چند قاعده · **چند قاعدهٔ منفی** | ⭐ نشان می‌دهد کجا خالی است |
| **قرنطینه** | شکست‌ها با دلیت | ⭐ چون شکستِ سیستمیک را نشان می‌دهد |
| ⭐ **تقاطع با تشخیص** | «برای این علامت چه چیزهایی آمده؟» | ⭐ ابزارِ اصلیِ کاربردیِ شما |

⛔ **سه چیزی که پنل نباید داشته باشد:** اجرای مستقیمِ SQL · ویرایشِ دستیِ قاعدهٔ موتور بدون شاهد · «انتشارِ همه» بدون بازبینی.
